# 1부. 설계

## 1. 배경

체커기 랜딩 페이지는 fake-door 방식으로 서비스 수요를 검증한다. 방문자가 이메일을 남기고 "알림 받기"를 누르면, 서비스가 시작될 때 그 이메일로 시작 알림을 보낸다. 등록 직후에는 연령대·성별을 묻는 2차 정보 모달이 열리며, 이 값은 Chip으로 선택하고 입력하지 않아도 된다.

이 데이터는 다음과 같은 성격을 가진다.

- **양이 적다.** 베타 대기 명단 규모로 수백~수천 건, 많아도 수만 건이다.
- **쓰기가 대부분이다.** 사용자 한 명당 쓰기는 최대 2번(등록, 2차 정보)일 수 있다. 읽기는 시작 알림 발송과 통계 확인 때만 일어난다.
- **수명이 짧다.** 개인정보처리방침상 정식 출시 후 3개월까지만 보유한다.
- **스키마가 거의 바뀌지 않는다.** 수집 항목이 개인정보처리방침에 고정되어 있다.

## 2. 범위

| 포함 | 제외 (후속 과제) |
|---|---|
| 이메일과 2차 정보(Chip 선택값)를 어떤 형태로 저장할지 | 저장된 데이터를 꺼내 쓰는 방식 (시작 알림 발송, 명단 내보내기, 통계) |
| 저장할 때 지켜야 할 제약과 상황별 처리 | 메일 발송 서비스와 메일 내용 |
| 비용을 적게 유지하고, 특정 DB 서비스에 묶이지 않게 하는 방법 | 스팸 등록 차단 |

## 3. 지켜야 할 제약

| 제약 | 출처 | 설계에 주는 영향 |
|---|---|---|
| 수집 항목은 이메일(필수), 연령대·성별(선택), 접속 일시뿐이다 | `packages/docs/src/privacy.ts` | IP, User-Agent, 유입 위치 등은 저장하지 않는다 |
| 삭제 요청 시 지체 없이 파기한다 | 개인정보처리방침 5번 | 삭제 표시가 아니라 행을 실제로 지운다 |
| 정식 출시 후 3개월까지 보유한다 | 개인정보처리방침 3번 | 기간이 지나면 테이블 전체를 지운다 |
| 2차 정보는 등록과 별도 요청으로 들어온다 | `LandingPage` → `ProfileModal` 흐름 | 2차 정보를 1차 등록 행과 연결할 키가 필요하다 |
| 2차 정보는 다시 열어서 고칠 수 있고, 선택을 해제할 수도 있다 | `ProfileModal`의 Chip 토글, 저장값 복원 | "값을 지움"과 "값을 보내지 않음"을 구분해야 한다 |
| 서버는 Vercel 서버리스(Route Handler)에서 돌아간다 | 배포 환경 | 요청마다 연결을 새로 맺어도 문제없는 DB 접근 방식이어야 한다 |
| 다른 인프라로 옮길 수 있어야 한다 | 이번 요구사항 | DB 전용 기능을 피하고, DB 접근 코드를 한 곳에 모은다 |

## 4. 테이블

저장소는 **Neon(PostgreSQL)** 이고, 테이블 하나로 저장한다.

```sql
CREATE TABLE waitlist (
  email       VARCHAR(254) PRIMARY KEY,
  age_group   VARCHAR(16)  NULL CHECK (age_group IN ('10대', '20대', '30대', '40대', '50대 이상')),
  gender      VARCHAR(16)  NULL CHECK (gender IN ('여성', '남성', '기타')),
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

| 컬럼 | 설명 |
|---|---|
| `email` | 기본 키. 앞뒤 공백을 지우고 소문자로 맞춘 값. 254자는 이메일 주소의 최대 길이이며, zod 스키마에서도 같은 길이로 막는다 |
| `age_group` | 연령대 코드. 선택하지 않았으면 `NULL` |
| `gender` | 성별 코드. 선택하지 않았으면 `NULL` |
| `created_at` | 등록 시점. UTC 기준으로 저장한다. 개인정보처리방침의 "접속 일시"에 해당한다 |

**두지 않는 컬럼**

- `id`: 이메일이 기본 키 역할을 한다. 대기 인원은 `SELECT COUNT(*) FROM waitlist`로 센다. ([2부 6](#6-id가-필요한가))
- `updated_at`: 이메일 수정 기능이 없고, 2차 정보 입력 여부는 `NULL`인지로 알 수 있다. ([2부 5](#5-updated_at이-필요한가))
- `policy_version`: 개인정보처리방침의 버전을 바꾸지 않으므로 필요 없다. 동의 시점은 `created_at`으로 남는다. ([2부 11](#11-동의한-방침-버전을-남길까))

**Chip 값은 화면 문구 그대로 저장한다** ([2부 10](#10-그-밖에-검토한-모델링))

| 항목 | 저장 값 |
|---|---|
| 연령대 | `10대` / `20대` / `30대` / `40대` / `50대 이상` |
| 성별 | `여성` / `남성` / `기타` |

화면, API(zod 스키마), DB가 같은 값을 쓴다. 선택지는 zod 스키마 한 곳에서 관리하고, DB의 `CHECK` 제약을 그 값과 맞춘다. PostgreSQL의 `ENUM` 타입 대신 `CHECK` 제약을 쓴다.

**시간은 UTC 시점으로 저장하고 KST로 보여 준다** ([2부 8](#8-created_at의-시간은-어떻게-다룰까))

| 용도 | 방법 |
|---|---|
| 화면 표시 | `new Intl.DateTimeFormat("ko-KR", { timeZone: "Asia/Seoul", dateStyle: "medium", timeStyle: "short" }).format(createdAt)` |
| SQL 조회, CSV 내보내기 | `created_at AT TIME ZONE 'Asia/Seoul'` |
| Neon 콘솔에서 확인 | 세션에서 `SET TIME ZONE 'Asia/Seoul';` 실행 |
| 일별 집계 | `(created_at AT TIME ZONE 'Asia/Seoul')::date`로 묶는다. UTC로 묶으면 하루가 한국 시간 오전 9시에 끊긴다 |
| 보유 기간 삭제 | 삭제 시점을 KST 날짜로 정하고, 실행할 때 UTC 시점으로 바꾼다 |

`+09:00`을 직접 더하지 않고 `Asia/Seoul` 이름을 쓴다.

## 5. 쓰기 흐름

```text
[입력란 첫 클릭] GET  /api/waitlist   (페이지에서 한 번만)
               → SELECT 1   (아무것도 기록하지 않음. 잠든 Neon을 미리 깨움)

[알림 받기]  POST  /api/waitlist          { email }
               → INSERT (email) ... ON CONFLICT (email) DO NOTHING
               → 추가된 행이 있으면 200 { success: true }
               → 추가된 행이 없으면(이미 등록된 이메일) 409 { code: "ALREADY_REGISTERED" }

[저장하기]   PATCH /api/waitlist/profile  { email, ageGroup, gender }
               → UPDATE waitlist SET age_group, gender WHERE email = ?
               → 200 { success: true }
```

| 요청 | 상황 | 응답 |
|---|---|---|
| 등록 | 새 이메일 | 200. 2차 정보 모달이 열린다 |
| 등록 | 이미 등록된 이메일 | 409. 2차 정보 모달이 열리지 않고, 입력란 아래에 "이미 등록된 이메일입니다."가 나온다 |
| 2차 정보 | 등록된 이메일, 등록되지 않은 이메일 | 200. 등록되지 않은 이메일이면 아무것도 바꾸지 않는다 |
| 등록·2차 정보 | 형식 오류, 254자를 넘는 이메일 | 400 |
| 등록·2차 정보 | DB 일시 장애 (연결 실패 등) | 503. 다시 시도하면 성공할 수 있다 |
| 등록·2차 정보 | 서버 설정 문제 (`DATABASE_URL` 누락, 테이블 없음 등) | 500. 다시 시도해도 성공하지 않는다 |

500과 503 모두 화면에는 기존 "신청하지 못했어요. 잠시 후 다시 시도해 주세요." 문구가 나온다. 서버 로그는 남기지 않으므로, Vercel이 요청마다 기록하는 응답 코드로 원인을 구분한다. ([2부 12](#12-서버-오류를-어떻게-구분할까))

- **1차 등록은 중복을 409로 막는다.** 이미 등록된 사람이 2차 정보를 덮어쓰지 않게 해서, DB의 연령대·성별 값을 새로 등록한 사람이 등록 직후 입력한 값으로만 유지한다.
- **409 응답 본문에는 이메일을 담지 않는다.** 이메일이 키이므로, 응답에는 고정된 오류 코드만 담는다.
  ```json
  { "code": "ALREADY_REGISTERED" }
  ```
- **2차 정보 API는 등록 여부를 구분하지 않는다.** 등록되지 않은 이메일이어도 200을 응답한다. ([2부 7](#7-이메일을-키로-쓰면-노출-위험은-없나))
- **2차 정보는 두 값을 통째로 덮어쓴다.** 항상 두 값을 모두 보내고, 선택하지 않은 값은 `null`로 보낸다. ([2부 9](#9-chip-선택-해제를-서버가-알-수-있나))

```ts
z.object({
  email: z.email(),
  ageGroup: ageGroupSchema.nullable(),
  gender: genderSchema.nullable(),
});
```

## 6. 상황별 처리

| 상황 | 처리 | 이유 |
|---|---|---|
| `Test@Example.com`과 `test@example.com` | 같은 사람으로 본다 | 저장 전에 공백을 지우고 소문자로 맞춘다 |
| `a.b@gmail.com`과 `ab@gmail.com`, `+태그` 주소 | 다른 사람으로 본다 | 메일 서비스마다 규칙이 달라 함부로 합치면 다른 사람을 같은 사람으로 볼 수 있다 |
| 이미 등록된 이메일로 다시 등록함 | 409를 응답하고, 2차 정보 모달을 열지 않는다 | 기존 사람의 2차 정보가 덮어써지지 않는다 |
| 등록 버튼을 빠르게 두 번 누름 | 한 행만 남는다 | 화면이 첫 요청 처리 중에는 다음 요청을 보내지 않는다. 그래도 들어오면 기본 키 충돌로 409가 된다 |
| 2차 정보를 두 번 저장함 | 나중 요청이 이긴다 | 두 값을 통째로 덮어쓰므로 결과가 항상 일관된다 |
| 2차 정보를 건너뜀 | 아무것도 저장하지 않는다 | `age_group`, `gender`가 `NULL`로 남는다 |
| 2차 정보 저장 중 DB 실패 | 등록은 유지되고, 모달에 실패 문구가 나온다 | 1차 등록과 2차 정보는 별도 요청이다 |
| 등록되지 않은 이메일로 2차 정보를 저장함 | 아무것도 바꾸지 않고 200을 응답한다 | 등록 여부를 드러내지 않는다 |
| 남의 이메일로 2차 정보를 저장함 (API 직접 호출) | 막지 않는다 ([결정 D2](#9-결정이-필요한-항목)) | 연령대·성별은 피해가 작은 정보라 단순함을 우선했다 |
| 삭제 요청 | 행을 지운다 | 개인정보처리방침 5번 |
| 정식 출시 후 3개월 | 테이블 전체를 지운다 | 개인정보처리방침 3번 |

## 7. 구현 규칙

**DB 접근은 인터페이스 하나로 모은다**

```ts
// apps/landing/src/server/waitlist/store.ts
export interface WaitlistStore {
  subscribe(email: string): Promise<void>;
  updateProfile(email: string, profile: { ageGroup: AgeGroupCode | null; gender: GenderCode | null }): Promise<void>;
}
```

- Route Handler는 이 인터페이스만 알고, 어떤 DB를 쓰는지는 구현 파일 하나만 안다.
- Neon 구현은 `@neondatabase/serverless`의 HTTP 방식을 쓴다. 서버리스에서 연결 풀을 관리할 필요가 없다.
- 테이블 생성 SQL은 저장소에 파일로 남긴다. 예: `apps/landing/src/server/waitlist/schema.sql`

**개인정보 보호**

- 이메일은 DB 밖에서 사용자를 가리키는 값으로 쓰지 않는다. 링크의 쿼리 문자열, 관리자 앱 주소, GA 이벤트 값, 서버 로그, 다른 테이블의 참조 값, **오류 응답 본문**에 이메일을 넣지 않는다.
- 외부에서 특정 사용자를 가리켜야 하는 기능(수신거부 링크 등)이 생기면, 그 기능을 맡은 쪽에서 공개용 식별자 컬럼이나 서명 토큰을 추가한다.
- 접속 정보는 `DATABASE_URL` 서버 환경 변수로만 둔다. `NEXT_PUBLIC_`을 붙이면 브라우저 코드에 포함되어 누구나 DB에 접속할 수 있다.

**Neon 미리 깨우기** ([2부 13](#13-잠든-neon을-언제-깨울까))

- 이메일 입력란(히어로, 하단 베타 영역 중 어느 쪽이든)을 처음 누르면 `GET /api/waitlist`를 보낸다. 입력란을 누르지 않고 자동 완성으로 값이 채워지는 경우를 위해 값이 바뀔 때도 보내며, 둘 중 처음 일어난 것 한 번만 보낸다.
- 성공하면 204(본문 없음), 실패하면 등록과 같은 기준으로 500 또는 503을 응답한다.
- 서버는 `SELECT 1`만 실행한다. 테이블을 읽거나 쓰지 않고, 방문자 정보도 남기지 않는다.
- 등록 API와 같은 파일에 두어, Vercel 함수도 함께 깨운다.
- 응답은 기다리지 않고 실패해도 무시한다. 입력과 등록에는 영향이 없다.

**다른 인프라로 옮길 때**

| 바꿀 것 | 방법 |
|---|---|
| DB 접근 코드 | 구현 파일 하나만 새로 쓴다. 일반 PostgreSQL은 `pg`, Turso는 `@libsql/client` |
| 중복 무시 문법 | MySQL은 `ON CONFLICT` 대신 `INSERT IGNORE` |
| 시간 타입 | MySQL은 `TIMESTAMP`(UTC로 바꿔 저장), SQLite는 ISO 8601 UTC 문자열(`2026-10-03T05:00:00Z`) |

나머지 SQL(`VARCHAR`, `CHECK`, `CURRENT_TIMESTAMP`)은 PostgreSQL, SQLite, MySQL 8에서 그대로 동작한다.

## 8. 비용

| 항목 | 추정 |
|---|---|
| 행 하나의 크기 | 기본 키 인덱스 포함 약 100~150바이트 |
| 1만 명 등록 시 전체 크기 | 약 1~2MB. Neon 무료 플랜 저장 용량의 1%에도 못 미친다 |
| 사용자당 DB 요청 | 쓰기 최대 2번 |
| 사용이 없을 때 | Neon은 컴퓨트가 자동으로 멈춰 비용이 들지 않는다. 다시 깨어날 때 첫 요청이 수백 ms~1초 안팎 늦어질 수 있다 |
| 미리 깨우기 | 이메일 입력란을 누른 사람 수만큼 깨어난다. 한 번 깨면 약 5분 동안 사용 시간이 쌓인다. 방문만으로는 깨우지 않는다 |

## 10. 현재 코드에 반영할 것

- `waitlistProfileRequestSchema`의 `ageGroup`, `gender`를 `optional()`에서 `nullable()`로 바꾼다.
- `WaitlistStore` 인터페이스와 Neon 구현을 추가하고, Route Handler에 연결한다.
- DB 일시 장애는 503, 서버 설정 문제는 500을 응답하도록 Route Handler에 처리를 추가한다.
- 이메일 스키마에 254자 제한을 추가한다.
- 1차 등록 Route Handler에서 추가된 행이 없으면 409 `{ code: "ALREADY_REGISTERED" }`를 응답한다.
- `EmailSignupForm`에서 409를 받으면 공통 `Form`의 `errors`로 입력란 아래에 "이미 등록된 이메일입니다."를 보여 주고, 2차 정보 모달을 열지 않는다.
- 등록 확인 메일은 없는 기능이므로 Route Handler와 메일 발송 코드에서 뺀다.
- `/api/waitlist`에 `SELECT 1`만 실행하는 `GET`을 추가하고, 이메일 입력란을 처음 누르거나 값이 바뀔 때 한 번 호출한다.

## 11. 후속 과제

- **꺼내 쓰기**: 시작 알림 발송 대상 조회, 발송 여부 기록(`notified_at` 컬럼 추가), 명단 CSV 내보내기
- **통계**: 등록 수, 2차 정보 응답률, 연령대·성별 분포. 일별 집계는 KST 날짜 기준으로 묶는다
- **메일 발송**: 발송 서비스 선택, 메일 내용, 개인정보처리방침에 수탁자 고지. 수신거부 링크에는 공개용 식별자나 서명 토큰이 필요하다
- **보유 기간 관리**: 출시 후 3개월 시점의 일괄 삭제 절차. 삭제 시점은 KST 날짜로 정한다
- **스팸 차단**: 숨김 입력 필드(honeypot)나 요청 빈도 제한. IP를 다루게 되면 개인정보처리방침 검토가 필요하다

## 1. 이 문제의 범위는 어디까지인가

- **고민**: 처음에는 메일 발송 라이브러리 선택(Resend, Nodemailer 등)이 주제처럼 보였다.
- **판단**: 시작 알림은 서비스가 시작될 때 보낸다. 그 전에 필요한 건 신청을 빠짐없이 저장하는 것이다. 저장이 없으면 들어온 신청이 모두 사라진다.
- **결론**: 이번 범위는 입력받은 이메일과 Chip 선택값을 어떤 DB에 어떤 형태로 저장하고, 어떤 제약이 있는지다. 꺼내 쓰기와 메일 발송은 후속 과제로 넘긴다.

## 2. 어떤 DB를 쓸까

| 선택지 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **Neon (PostgreSQL)** | Vercel과 바로 연결되고, 표준 SQL이라 이식성이 높다 | 개발자가 아닌 사람은 명단을 보기 불편하다 | **채택** |
| Supabase (PostgreSQL) | 대시보드가 편하고 인증 기능까지 있다 | 랜딩 페이지에 쓰기에는 무겁다 | 채택하지 않음 |
| Google 스프레드시트 | 추가 인프라가 없고 누구나 명단을 볼 수 있다 | 중복 방지와 형식 보장이 없고, 사람이 직접 고치다 데이터가 깨질 수 있다 | 채택하지 않음 |
| Turso (SQLite) | 가볍고 무료 범위가 넓다 | 팀에 익숙하지 않을 수 있다 | 채택하지 않음 |
| Redis/KV (Upstash 등) | 쓰기가 매우 빠르다 | 목록 조회, 내보내기, 통계에 맞지 않는다 | 채택하지 않음 |

대기 명단 규모에서는 모든 선택지가 무료 범위 안에 들어온다. 그래서 비용보다 관리 편의와 이식성을 기준으로 골랐다.

## 3. 상태관리 라이브러리가 필요한가

- **고민**: 2차 정보 모달에서 Chip 선택 상태를 다루는데, Zustand 같은 상태관리 라이브러리가 필요할까.
- **판단**: Chip 선택값은 모달 안에서만 쓰이고 다른 화면과 나눠 쓰지 않는다.
- **결론**: 화면 상태는 `useState`, 서버 요청은 이미 설치된 TanStack Query로 처리한다.

## 4. 타입을 따로 둬야 하나

- **고민**: zod 스키마가 있는데 타입이 따로 필요할까.
- **판단**: 타입이 없으면 필드 이름 오타 같은 실수가 배포 뒤 방문자에게 발견된다. 랜딩 페이지는 놓친 신청을 되찾을 수 없다. 타입을 손으로 따로 쓰면 스키마와 어긋날 수 있다.
- **결론**: zod 스키마에서 `z.infer`로 뽑아 쓴다. 정의는 한 곳에만 두고, 프론트와 서버가 같은 타입을 쓴다.

## 5. `updated_at`이 필요한가

- **고민**: 처음 설계에는 `updated_at`이 있었는데, 이메일 수정 기능은 아직 고려하지 않았다.
- **판단**: 2차 정보를 입력했는지는 `age_group`, `gender`가 `NULL`인지로 알 수 있다. 개인정보처리방침의 수집 항목에도 없다.
- **결론**: 현재는 두지 않고 필요할때 컬럼을 추가하는 방식으로 해야겠다고 판단.

## 6. `id`가 필요한가

1. **자동 증가 번호**를 통해서 특정 행을 쉽게 가리킬 수 있도록 생각했다.
   - 현재 나온 기능중에 DB를 조회하는 기능은 없다. 향후에 나와서 id 컬럼이 필요할 때 추가하면 된다고 판단했다.
   - 필요하지 않은것에 비해서 노출과 보안적 위험이 있었다.
    - id는 밖에서 행을 가리키는 값이라, 수신거부 링크, 관리자 앱 주소, 등록 응답 등 기능이 붙을수록 노출 위험도가 크다.
    - 노출되면 가입자 수와 성장 속도가 드러날 수 있고, 초기 기획 단계에서 걱정한 내용과 정확히 일치되는 내용이다. 
2. 대안으로 UUID, NanoID, 내부 번호와 공개용 id 분리, 서명 토큰을 검토했다. 다만 내부 운영용으로 읽기 쉬운 번호가 필요할 수도 있었다.
3. "마지막 번호로 대기 인원을 보여 주자"는 용도는 맞지 않았다. 중복 등록, 삭제, 실패한 저장으로 번호가 건너뛰어져 실제 인원보다 커진다. 대기 인원은 `COUNT(*)`로 센다.
4. `id`를 두면 숨기는 책임이 함께 생기는데, 이번 범위에는 `id`를 쓸 곳이 없다.
5. **결론**: id값은 두지 않는다. 이메일을 기본 키로 쓴다. 외부에서 사용자를 가리켜야 하는 기능이 생기면 그 기능을 맡은 쪽에서 공개용 식별자를 추가한다.

## 7. 이메일을 키로 쓰면 노출 위험은 없나

- **고민**: `id`를 빼고 나니, 반대로 이메일이 노출될 가능성은 없는지 따져 봤다.
- **판단**: 아래 문제들은 `id`를 추가해도 해결되지 않는다. 문제는 키가 아니라 이메일과 등록 여부를 밖으로 내보내는 곳에 있었다.
- **공통 개선**
  - 메일 발송 코드가 받는 사람 이메일을 서버 로그에 남기고 있었다. 로그는 팀원 누구나 볼 수 있고, 삭제 요청이 와도 지워지지 않는다. 로그에서 이메일을 뺐다.
  - 이메일을 DB 밖에서 사용자를 가리키는 값으로 쓰지 않는다는 규칙을 정했다.

### 7-1. 2차 정보 API가 등록 여부를 드러낸다

- **발견한 문제**: 2차 정보 API가 등록되지 않은 이메일에 404를 응답하도록 설계되어 있었다. 아무 이메일이나 넣어 보는 것만으로 그 사람이 대기 명단에 있는지 알 수 있었다.
- **이게 개인정보 유출인가**
  - 알아내려면 상대의 이메일을 이미 알고 있어야 한다. 새로 알게 되는 것은 "이 이메일 주인이 체커기 대기 명단에 있다"는 사실 하나다.
  - 이메일은 개인을 알아볼 수 있는 정보라 이 사실도 그 사람에 관한 정보다. 그래서 **노출**은 맞다.
  - 하지만 명단이나 이메일 목록이 넘어가는 것은 아니므로 **유출**이라고 부르기에는 과하다. 정확한 표현은 **등록 여부 노출**이다.
  - 위험도는 서비스 성격에 따라 다르다. 병원, 데이팅, 대출처럼 가입 사실 자체가 민감한 서비스와 달리, 강의 비교 서비스의 대기 명단은 "강의에 관심이 있다" 정도라 피해가 작다.
  - 가장 현실적인 위험은 이메일 목록을 넣어 등록자만 골라낸 뒤 체커기를 사칭한 피싱 메일을 보내는 것이다. 이는 요청 빈도 제한 같은 스팸 차단(후속 과제)으로 줄인다.
- **개선**: 위험도는 낮지만, 2차 정보 API에서는 막아도 잃는 것이 없다. 그래서 등록 여부와 관계없이 200을 응답하고, 등록되지 않은 이메일이면 아무것도 바꾸지 않는다.

### 7-2. 중복 등록을 막을까

- **고민**: 처음 설계는 등록 여부를 드러내지 않으려고, 이미 등록된 이메일로 다시 등록해도 200을 응답했다. 그런데 응답이 같으니 화면은 2차 정보 모달을 똑같이 연다. 거기서 저장하면 **기존 사람의 연령대·성별이 덮어써진다.** 본인이 다시 등록한 경우라면 문제가 없지만, 남이 내 이메일을 넣은 경우라면 내가 입력한 값이 사라진다.
- **기준**: 이번 범위의 목적은 DB에 쌓이는 값을 얼마나 정확하게 셀 수 있느냐다.
- **검토한 방법**

| 방법 | 판단 |
|---|---|
| 항상 덮어쓰기 (처음 설계) | 가장 단순하지만, 남의 입력으로 기존 값이 바뀌어 DB 값을 믿을 수 없다 |
| 비어 있을 때만 저장 | 한 번 입력한 값은 지켜지지만, 저장 후 모달을 다시 열어 고치는 기존 기능과 충돌한다 |
| 등록 직후 일정 시간만 저장 허용 | `created_at`으로 해결할 수 있지만, 그 시간 안의 덮어쓰기는 여전히 가능하다 |
| 새 등록에만 토큰 발급 | 가장 확실하지만, 중복 등록에도 가짜 토큰을 줘야 해서 구현이 복잡하다 |
| **1차 등록에서 중복을 막기** | 이미 등록된 사람에게는 모달이 열리지 않아, 덮어쓰기가 일어날 자리 자체가 없어진다. **채택** |

- **판단 근거**
  - Google Analytics가 아직 연결되어 있지 않다(이슈 #21). 지금은 DB가 2차 정보를 세는 유일한 기준이다.
  - 개인정보처리방침에 "접속 일시(중복 신청 방지 목적)"가 적혀 있어, 처음부터 중복 신청을 막는 것을 전제로 했다.
  - 공통 `Form` 컴포넌트에 서버 오류를 보여 주는 기능과 "이미 등록된 이메일입니다." 예시가 이미 있다.
- **결론**: 1차 등록에서 이미 등록된 이메일이면 409를 응답하고, 2차 정보 모달을 열지 않는다.
- **주의**: 이메일이 키이므로 409 응답 본문에는 이메일을 담지 않고, 고정된 오류 코드(`{ "code": "ALREADY_REGISTERED" }`)만 담는다.
- **트레이드오프**: 1차 등록에서는 등록 여부가 노출된다. [7-1](#7-1-2차-정보-api가-등록-여부를-드러낸다)과 같은 수준의 낮은 위험이지만, 여기서는 막으면 DB 값의 정확도를 잃는다. 그래서 7-1에서는 막고 7-2에서는 받아들였다. 위험도는 같고, 막았을 때 잃는 것이 다르기 때문이다.

## 8. `created_at`의 시간은 어떻게 다룰까

- **고민**: 사용자는 한국인이지만, Neon과 Vercel은 UTC로 동작한다. 어디서든 동작 가능한 시간대로 개선되어야만 한다.

| 위치 | 기본 시간대 |
|---|---|
| Neon (PostgreSQL), Neon 콘솔 | UTC |
| Vercel 서버 함수 | UTC |
| 로컬 개발 PC | KST |
| 사용자 브라우저 | 대부분 KST |

- **발견한 문제**: 처음 설계는 이식성 때문에 `TIMESTAMP`를 썼다. PostgreSQL의 `TIMESTAMP`는 시간대 없이 시계 숫자만 저장한다.
  - 서버 코드가 넣으면 UTC 숫자가, 콘솔에서 시간대를 KST로 바꾸고 넣으면 KST 숫자가 들어간다. 둘을 구분할 수 없다.
  - DB 드라이버는 시간대 없는 값을 실행 중인 컴퓨터의 시간대로 해석한다. Vercel에서는 맞게 보이고, 로컬 개발 PC에서는 9시간 어긋나 보일 수 있다.
- **개선**: `TIMESTAMPTZ`로 바꿨다. 절대 시점을 저장하므로 누가 어디서 넣든 같은 시점이 기록된다. 시간 타입은 DB마다 한 줄 다르게 쓰는 것으로 이식성과 타협했다.

| 검토한 다른 방법 | 판단 |
|---|---|
| KST 숫자로 저장 | 서버와 DB가 모두 UTC라 매번 변환해야 하고, 그 값이 KST라는 사실을 모두가 기억해야 한다. 채택하지 않음 |
| DB 기본 시간대를 KST로 변경 (`ALTER DATABASE ... SET timezone`) | 보이는 방식만 바뀌고, 다른 인프라로 옮길 때 이 설정을 놓치기 쉽다. 채택하지 않음 |

## 9. Chip 선택 해제를 서버가 알 수 있나

- **발견한 문제**: `ProfileModal`은 저장된 값을 다시 보여 주고, 사용자는 Chip을 눌러 선택을 해제할 수 있다. 그런데 JSON은 `undefined`를 보내지 않는다. 그래서 "선택을 해제함"과 "값을 보내지 않음"을 서버가 구분할 수 없었다.
- **개선**: 2차 정보 요청은 항상 두 값을 모두 보내고, 선택하지 않은 값은 `null`로 보낸다. 서버는 받은 두 값으로 통째로 덮어쓴다.

## 10. 그 밖에 검토한 모델링

| 선택지 | 판단 |
|---|---|
| 테이블 두 개 (등록 / 2차 정보) | 1:1 관계라 조인만 늘어난다. 채택하지 않음 |
| 2차 정보를 JSON 컬럼 하나에 저장 | 값 검사(`CHECK`)와 통계 쿼리가 어려워진다. 채택하지 않음 |
| Chip 값을 영문 코드로 저장 (`20s`, `female`) | 화면 문구가 바뀌어도 DB를 고칠 필요가 없지만, 코드와 화면 문구를 두 곳에서 관리해야 한다. Chip 문구는 바뀔 일이 없어 채택하지 않음 |
| **Chip 값을 화면 문구 그대로 저장** | 문구가 바뀌면 코드 값, DB 제약, 기존 행을 모두 고쳐야 하지만, 문구가 바뀔 일이 없다. 추가 코드 없이 DB를 바로 읽을 수 있다. **채택** ([결정 D1](#9-결정이-필요한-항목)) |
| PostgreSQL `ENUM` 타입 | 값을 고치기 어렵고 PostgreSQL에만 있다. `CHECK` 제약으로 대신함 |

## 11. 동의한 방침 버전을 남길까

1. **고민**: 등록 폼에는 "등록하면 개인정보 수집·이용에 동의하는 것으로 봅니다"라는 안내가 있다. 등록하는 순간이 곧 방침에 동의하는 순간이다. 방침이 바뀌면 누가 어느 버전에 동의했는지 알아야 할 수 있다.
2. **처음 판단**: 방침이 팀 내 의견 수렴 중이라 버전이 바뀔 가능성이 있다고 봤다. 그래서 등록할 때 방침 시행일을 `policy_version` 컬럼에 남기기로 했다.
3. **다시 생각한 점**: 버전을 기록하는 것보다 **버전이 바뀌는 것 자체**가 더 큰 문제였다.
   - 방침이 바뀌면 이미 등록한 사람들은 바뀌기 전 방침에만 동의한 상태가 된다. 바뀐 내용에 대해서는 다시 동의를 받아야 한다.
   - 대기 명단 단계에서 사용자와 연결된 수단은 이메일뿐이다. 재동의를 요청해도 응답하지 않는 사람을 어떻게 처리할지까지 정해야 해서, 컬럼 하나를 추가하는 것보다 훨씬 어렵다.
4. **결론**: 개인정보처리방침의 버전은 바꾸지 않는다. 버전이 하나뿐이므로 `policy_version` 컬럼도 두지 않는다. 동의 시점은 `created_at`으로 남는다.
5. **후속 과제와의 관계**: 메일 발송 때 외부 발송 서비스를 쓰면 수탁자를 방침에 적어야 한다. 현재 방침은 이미 "메일 발송을 위해 외부 발송 서비스에 처리를 위탁할 수 있으며, 위탁 시 수탁자와 처리 내용을 본 방침에 고지합니다"라고 위탁 가능성을 알리고 있다. 위탁은 동의가 아니라 공개(고지) 대상이라 재동의 없이 수탁자를 추가할 수 있다고 보지만, 실제로 추가할 때는 수집 항목이나 이용 목적이 바뀌지 않는지 확인한다.

## 12. 서버 오류를 어떻게 구분할까

- **고민 1: 서버 로그를 남길까**
  - 저장에 실패하면 사용자에게는 UI에서 실패 문구를 보여 준다. 팀이 실패 원인을 따로 알 필요는 없다고 판단해 `console.error` 로그를 남기지 않기로 했다.
- **고민 2: catch에서 모든 오류를 503으로 묶어도 될까**
  - 503은 "잠시 후 다시 시도하면 될 수 있다"는 뜻이다. 그런데 다시 시도해도 절대 성공하지 않는 오류까지 503으로 나가고 있었다.
- **발견한 문제**

| 실제 원인 | 처음 응답 | 맞는 응답 |
|---|---|---|
| Neon 일시 장애, 연결 실패 | 503 | 503 |
| 254자를 넘는 이메일 | 503 | 400. zod `z.email()`은 312자 이메일도 통과시키고, DB의 `VARCHAR(254)`에서 저장 오류가 났다 |
| `DATABASE_URL` 누락, 테이블 없음 | 503 | 500. 서버 설정 문제라 다시 시도해도 실패한다 |

- **개선**
  - 이메일 스키마에 `.max(254)`를 추가해, DB까지 가기 전에 400으로 걸러낸다. 화면에서도 같은 스키마로 검사하므로 제출 전에 안내된다.
  - 254자는 사용자가 아는 규칙이 아니라 이메일 표준의 최대 길이다. 그보다 긴 주소는 올바른 이메일이 아니므로, 안내 문구는 형식 오류와 같은 "올바른 이메일 형식이 아닙니다."를 쓴다.
  - 저장소에 일시 장애를 뜻하는 `WaitlistStoreUnavailableError`를 두고, Route Handler는 이 오류면 503, 그 밖의 오류면 500을 응답한다.
  - 어떤 오류가 일시 장애인지는 DB 구현 파일(`neon-store.ts`)만 판단한다. 연결 자체가 실패한 경우와 PostgreSQL 오류 코드 중 연결·자원·재시도 관련(`08`, `53`, `57P`, `40001`, `40P01`)을 일시 장애로 본다. 다른 인프라로 옮기면 이 판단만 새로 쓴다.
- **판단 근거**: 로그를 남기지 않으므로, Vercel이 요청마다 기록하는 응답 코드가 팀이 원인을 짐작할 수 있는 유일한 단서다. 500이 쌓이면 설정 문제, 503이 쌓이면 DB 장애로 구분할 수 있다. 사용자에게 보이는 문구는 둘 다 같다.

## 13. 잠든 Neon을 언제 깨울까

- **고민**: Neon 무료 플랜은 5분 동안 요청이 없으면 자동으로 멈춘다. 방문자가 적은 랜딩 페이지에서는 거의 항상 잠든 상태다.
  - 잠든 DB는 요청이 오면 자동으로 깨어나고, 첫 요청은 그동안 기다렸다가 처리된다. Neon 공식 문서 기준 깨어나는 데 수백 ms가 걸리고, Vercel 함수가 처음 뜨는 시간까지 더하면 대략 1초 안팎이다.
  - 몇 초씩 걸리는 것은 아니지만, 사용자가 "알림 받기"를 누른 시점에 깨우기 시작하면 그 시간만큼 등록 응답이 늦어져 사용감을 해친다.
  - 응답이 10초(axios 제한 시간)를 넘기면 화면은 실패로 처리한다. 이때 저장은 이미 됐을 수 있어서, 다시 누르면 409가 나오고 2차 정보 모달이 열리지 않는다.
- **판단 기준**: 즉시 반응하는 "항상 켜 두기"와 비교해, 깨어나는 시간을 사용자가 느끼지 못하게 하면서 비용이 적은 방법을 고른다.
- **검토한 방법**

| 방법 | 판단 |
|---|---|
| 자동 정지 끄기 (항상 켜 두기) | 즉시 반응하지만 무료 플랜에서는 끌 수 없다. 유료 Launch 플랜에서 최소 크기(0.25 CU)로 켜 두면 한 달 약 182.5 CU-시간, **월 약 $19**가 든다. 채택하지 않음 |
| 몇 분마다 주기적으로 깨우기 (cron) | 아무도 없을 때도 24시간 깨어 있어 한 달 약 182.5 CU-시간을 쓴다. 무료 한도(월 100 CU-시간)를 넘겨 **한 달 중 17일 정도에 DB가 멈추고, 그 뒤로는 등록 자체가 막힌다.** 채택하지 않음 |
| 서버에서 페이지를 그릴 때 깨우기 | 홈페이지는 미리 만들어 둔 정적 페이지라 방문 때 서버 코드가 돌지 않는다. 바꾸면 페이지가 느려진다. 채택하지 않음 |
| 브라우저가 페이지를 그릴 때 깨우기 | 검색 크롤러, 미리보기 봇 등 사람이 아닌 방문에도 DB가 깨어나, 등록과 상관없는 사용 시간이 쌓인다. 채택하지 않음 |
| 마우스를 입력란에 올릴 때 깨우기 (hover) | 조금 더 일찍 깨우지만 모바일에는 마우스가 없어 동작하지 않고, 스크롤하다 우연히 지나가도 깨운다. 채택하지 않음 |
| **이메일 입력란을 처음 누를 때 깨우기 (focus)** | 등록할 마음이 있는 사람만 깨운다. PC와 모바일 모두 동작한다. 이메일을 입력하는 시간(직접 입력 수 초, 자동 완성 1~2초)이 깨어나는 시간보다 길어, 제출할 때는 이미 깨어 있다. 체감은 항상 켜 두기와 거의 같고 비용은 무료다. 한 번 깨우면 약 0.02 CU-시간이라, 무료 한도로 한 달에 약 4,800번 따로 떨어진 깨우기를 버틴다. **채택** |

- **개선**: 등록 시점에 깨우던 것을, 사용자가 이메일을 입력하기 시작하는 시점에 미리 깨우도록 바꿨다. 제출할 때는 이미 깨어 있어 등록 응답이 늦어지지 않는다.
- **봇도 이메일 입력란에 접근하는가**

| 봇 종류 | 입력란을 누르나 |
|---|---|
| 검색 크롤러 (Googlebot 등) | 아니다. 화면을 그려 보기는 하지만 클릭하거나 입력하지 않는다 |
| 링크 미리보기 봇 (카카오톡, 슬랙 등) | 아니다. 제목과 이미지만 가져간다 |
| 성능 측정 도구 (Lighthouse 등) | 아니다 |
| 폼 스팸 봇 | 그럴 수 있다. 다만 결국 등록까지 제출하므로, 깨우기가 없어도 그 등록 요청 때문에 DB는 깨어난다. 문제는 깨우기가 아니라 스팸 등록이며, 후속 과제인 스팸 차단에서 다룬다 |

- **확인한 점**
  - 깨우기 요청(`SELECT 1`)은 DB에 아무것도 기록하지 않는다. 테이블을 건드리지 않고 방문자 정보도 남기지 않으므로, 개인정보처리방침과 등록 수에 영향이 없다.
  - 비용은 요청 수가 아니라 DB가 깨어 있던 시간으로 쌓인다. 한 번 깨우면 약 5분 동안 사용 시간이 쌓인다.
  - 깨어나는 시간은 공식 수치(수백 ms)로 판단했다. 몇 초씩 걸리지 않으므로 직접 측정은 하지 않았다.
  - 비용 수치는 2026년 10월 기준 [Neon 요금제](https://neon.com/pricing)를 따랐다.
- **한계**
  - 입력란을 누르자마자 1초 안에 제출하면 깨어날 시간이 부족할 수 있다. 이 경우에도 버튼 로딩이 조금 길어질 뿐 등록은 정상적으로 된다.
  - 저장 직후 네트워크가 끊기는 경우는 깨우기로 막을 수 없다. 깨우기는 느린 응답으로 생기는 경우를 줄이는 것이다.
